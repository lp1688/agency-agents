1. 總覽：專案結構與貢獻類型

The Agency 是一個純 Markdown 的 agent 集合。每個 agent 是一個 .md 檔，放在所屬「division（部門）」的頂層目錄下。轉換與安裝由各腳本處理，貢獻者只需要寫好一個 .md 檔。

路徑性質說明
engineering/、marketing/ 等 18 個目錄Division（agent 來源）agent .md 檔的存放處；權威清單是根目錄的 divisions.json
divisions.jsonDivision 的唯一真相來源定義每個 division 的 label、icon、顏色；CI 會用 check-divisions.sh 驗證它與磁碟目錄一致
tools.json工具整合的唯一真相來源定義 Claude Code / Cursor / Kimi / Codex 等 17 種工具的轉換目標
integrations/產出物，不是來源convert.sh 的輸出目錄，只有各工具的 README.md 會被 git 追蹤，其餘全部 gitignore
strategy/、examples/非 divisionplaybook 與範例，沒有 agent frontmatter
scripts/基礎設施convert.sh（轉換）、install.sh（安裝）、lint-agents.sh（格式檢查）、check-agent-originality.sh（原創性檢查）等

四種貢獻類型

  • 新增 agent —— 一個新 .md 檔（最受歡迎的貢獻）
  • 優化現有 agent —— 補真實案例、更新程式碼範例、改進 workflow、補成功指標、修錯字
  • 分享成功案例 —— Discussions 發文、README 案例研究、部落格、影片教學
  • 回報問題 —— 先搜尋既有 issue，附清楚的重現步驟與使用情境
💡 官方明說：最快被合併的 PR 就是「一個 markdown 檔」——新增或改進一個 agent。超過這個範圍的改動，多半需要先開 Discussion 對齊方向。

2. 新增 Agent：九步驟完整流程

1Fork 並 Clone 倉庫
# GitHub 上 Fork msitarzewski/agency-agents，然後：
git clone https://github.com/<你的帳號>/agency-agents
cd agency-agents
2選擇所屬 Division

瀏覽各 division 目錄，找最貼近的歸屬（例如網頁前端 → engineering/、社群經營 → marketing/、滲透測試 → security/、文獻與證據綜整 → research/）。18 個 division 的權威清單看 divisions.json。都不適合才考慮提案新 division（見第 4 節），specialized/ 是「放不進任何類別」的收容所。

3建立檔案，命名遵循慣例

檔名格式：<division>-<agent-name>.md，全小寫、kebab-case。例如：

engineering/engineering-frontend-developer.md
marketing/marketing-xiaohongshu-specialist.md
game-development/unity/unity-architect.md   ← game-development 有引擎子目錄
4撰寫 YAML Frontmatter
---
name: Agent Name
description: One-line description of the agent's specialty and focus
color: colorname or "#hexcode"
emoji: 🎯
vibe: One-line personality hook — what makes this agent memorable
services:                              # 選填 — 僅當 agent 依賴外部服務
  - name: Service Name
    url: https://service-url.com
    tier: free                         # free / freemium / paid
---

name、description、color 三個是 CI 必填（缺了直接 ERROR）；emoji、vibe、services 為選填。

5依範本撰寫內文（Persona 區 + Operations 區）

章節分兩大語意群，convert.sh 會依章節標題把 agent 拆成各工具格式，請維持分組與英文標題關鍵字（Identity / Core Mission / Critical Rules…）：

群組章節內容
Persona
（這個 agent 是誰）		🧠 Your Identity & MemoryRole / Personality / Memory / Experience
💭 Your Communication Style語氣、慣用句式、溝通方式
🚨 Critical Rules You Must Follow領域專屬的硬性規則與邊界
Operations
（這個 agent 做什麼）		🎯 Your Core Mission主要職責（每條含明確交付物）+ 預設要求
📋 Your Technical Deliverables具體產出：程式碼範例、模板、框架、文件
🔄 Your Workflow Process分階段的步驟流程
🎯 Your Success Metrics可量化的成果指標（要帶數字）
🚀 Advanced Capabilities進階技巧

完整範本骨架見第 5 節。

6本地驗證：lint + 原創性 + 轉換輸出檢查
# 格式檢查（必填欄位、換行符號、章節）
./scripts/lint-agents.sh engineering/engineering-your-agent.md

# 原創性檢查（與全部 279 個 agent 比對，防 find-replace 換皮）
./scripts/check-agent-originality.sh engineering/engineering-your-agent.md

# 轉換輸出檢查（確認你的 agent 能完好通過每一個工具的轉換器）
./scripts/test-convert-outputs.sh

原創性門檻：相似度 ≥ 20% 警告、≥ 40% 判定重複（CI 失敗）。現有庫內最高相似度僅約 1.5%，雙位數就是異常。檢查會把國家/平台專有名詞中性化，所以「把 TikTok 換成抖音」這種換皮逃不掉。

test-convert-outputs.sh 會把所有工具的輸出重新產生到暫存目錄，檢查的是產品本身而非語法：每個 agent 的 description 是否完整往返、每個產生檔能否被真正的 YAML/TOML parser 解析、每個工具是否恰好為每個 agent 產生一份輸出、每個來源檔是否以桌面 App 讀取的方式解析。新增或修改 agent 本來就會改變產出，所以它會回報指向你 agent 的 manifest drift——這是預期的，而且在 PR 上只是提示性（advisory）：CI 會印出來但不會因此失敗。你不需要動 scripts/convert-outputs.sha256，維護者會在 PR 合併後重新產生（自己跑 --update 也可以：manifest 每個 agent 一行，不會與別人的 PR 衝突，且在 Windows / macOS / Linux 上雜湊值一致）。

7真實場景實測

官方要求「battle-tested，不要紙上談兵」：實際把 agent 拿去用（例如用 Kimi Code 載入它跑真實任務，見第 11 節），根據結果迭代打磨。

8Commit 並推到你的 Fork
git checkout -b add-your-agent-name
git add engineering/engineering-your-agent.md
git commit -m "Add Your Agent Name specialist"
git push origin add-your-agent-name
9開 Pull Request
  • 標題格式：Add [Agent Name] - [Category]
  • 內文說明：這個 agent 做什麼、為什麼需要它（填補什麼空白）、你做過哪些測試
  • 填妥 PR 模板 checklist（見第 8 節）

之後進入審核循環：社群回饋 → 迭代修改 → 維護者核准 → 合併。

3. 優化現有 Agent

改進現有 agent 與新增一樣受歡迎，且同樣走「一個檔案的 PR」路線。官方列舉的改進方向：

  • 補充真實案例與使用場景
  • 用現代模式更新程式碼範例（例如舊語法 → 新版框架寫法）
  • 依最新最佳實踐更新 workflow
  • 補上成功指標與基準數字
  • 修錯字、提升清晰度、完善文件

流程

  1. 同樣 fork → 開分支（例如 improve-frontend-developer-examples）
  2. 修改目標 .md 檔；改完跑 ./scripts/lint-agents.sh <檔案> 確認格式沒壞
  3. Commit（例如 Improve frontend-developer: add React 19 examples）→ push → 開 PR
  4. PR 內文說明「改了什麼、為什麼更好」
⚠️ 不要在一個 PR 裡批量修改大量現有 agent——即使是善意的重新排版，也會對其他貢獻者造成 merge conflict，官方明言這類 PR 會直接關閉。想做大範圍重整，先開 Discussion。

4. 提案新 Division（部門）

新 division 屬於「架構性改動」，務必先開 Discussion 取得共識。通過後的技術步驟：

  1. 建立新目錄，裡面至少放 1 個含 frontmatter 的 agent 檔
  2. 在 divisions.json 新增條目：label（顯示名）、icon（Lucide 圖示名，PascalCase）、color（hex 色碼）
  3. 把目錄名加入 兩個腳本的 AGENT_DIRS 陣列：scripts/convert.sh 與 scripts/lint-agents.sh
  4. 更新 CI 路徑過濾（.github/workflows/lint-agents.yml 的 paths）
  5. 跑 ./scripts/check-divisions.sh 驗證——它會檢查「divisions.json ↔ 磁碟目錄 ↔ 各腳本清單」全部一致，不一致就 fail
⚠️ strategy/（playbook）與 integrations/（convert 產出）永遠不是 division，不可加入 division 清單。

5. Agent 檔案結構規範

Frontmatter 欄位

欄位必填說明
name✅ CI 必填Agent 顯示名稱
description✅ CI 必填一句話說明專長與定位
color✅ CI 必填顏色名或 hex 色碼
emoji選填代表 emoji
vibe選填一句話人格鉤子——這個 agent 令人記住的點
services選填外部服務依賴（name / url / tier: free | freemium | paid）

內文完整範本

---
name: Agent Name
description: One-line description of the agent's specialty and focus
color: cyan
emoji: 🎯
vibe: One-line personality hook
---

# Agent Name

## 🧠 Your Identity & Memory
- **Role**: 清晰的角色描述
- **Personality**: 性格特質與溝通風格
- **Memory**: 這個 agent 會記住與學習什麼
- **Experience**: 領域專業與視角

## 🎯 Your Core Mission
- 主要職責 1（含明確交付物）
- 主要職責 2（含明確交付物）
- **Default requirement**: 永遠開啟的最佳實踐

## 🚨 Critical Rules You Must Follow
領域專屬的規則與約束，定義 agent 的工作方式

## 📋 Your Technical Deliverables
具體產出：程式碼範例 / 模板 / 框架 / 文件

## 🔄 Your Workflow Process
1. 階段一：探索與研究
2. 階段二：規劃與策略
3. 階段三：執行與實作
4. 階段四：檢討與優化

## 💭 Your Communication Style
溝通方式、示例句式、語氣

## 🔄 Learning & Memory
從成功模式 / 失敗方法 / 使用者回饋 / 領域演進中學習

## 🎯 Your Success Metrics
量化指標（帶數字）、質性指標、效能基準

## 🚀 Advanced Capabilities
進階技巧與方法
✅ 章節標題建議保留英文關鍵字（Identity、Core Mission、Critical Rules、Communication Style…），因為 lint-agents.sh 與 convert.sh 靠這些關鍵字辨識章節並拆分 Persona / Operations。三個推薦章節 Identity / Core Mission / Critical Rules 缺少時 lint 會給 WARN（不擋合併，但審核會看）。

外部服務（services）的使用原則

  • agent 必須能獨立成立——抽掉 API 呼叫後，人格、workflow、專業知識仍然有用
  • 不要複製貼上廠商文件——引用即可；檔案讀起來要像 agent，不像快速入門教學
  • 優先選有免費方案的服務，方便貢獻者測試
  • 檢驗標準：「這個 agent 是為使用者服務，還是為廠商服務？」

6. 設計原則：該做與不該做

五大設計原則

  1. 🎭 鮮明人格——獨特聲線與角色，不要「我是有用的助手」。範例：「我預設會找出 3–5 個問題，並要求提供視覺證據」（Evidence Collector）
  2. 📋 明確交付物——具體程式碼範例、模板、框架；展示真實輸出，不是模糊描述
  3. ✅ 成功指標——具體可量化：「3G 網路下頁面載入低於 3 秒」、「全帳號合計 karma 10,000+」
  4. 🔄 經過驗證的 workflow——分步驟、真實場景測試過，不是理論
  5. 💡 學習記憶——能識別哪些模式、如何隨時間改進、跨 session 記住什麼

對照表

✅ 優秀 agent 有❌ 要避免
狹窄而深入的專精領域範圍過寬（樣樣通樣樣鬆）
獨特人格與聲線通用「樂於助人的助手」人格
具體程式碼 / 模板範例（至少 2–3 個）沒有程式碼範例、沒有交付物
可量化的成功指標模糊的「我會幫你……」描述
分步驟 workflow未經測試的理論方案
真實場景測試與迭代find-replace 換皮現有 agent

7. CI 檢查與本地驗證

PR 送出後，GitHub Actions 會對「本次變更的 agent 檔」自動執行以下檢查。全部都可以在本地先跑：

檢查腳本 / Workflow規則本地指令
格式 lintscripts/lint-agents.sh
(lint-agents.yml)		 ERROR（擋合併）：CRLF 換行、缺 --- frontmatter、缺 name/description/color
WARN（不擋）：缺 Identity / Core Mission / Critical Rules 章節、內文 < 50 字、章節無法對映到轉換器分組		 ./scripts/lint-agents.sh <檔案>
原創性scripts/check-agent-originality.sh
(lint-agents.yml)		與全部現有 agent 做 8 詞 shingle 比對；國家/平台名會被中性化。≥20% WARN、≥40% FAIL。現有庫基準最高僅 ~1.5% ./scripts/check-agent-originality.sh <檔案>
（不帶參數＝全庫稽核）
Division 一致性scripts/check-divisions.sh
(check-divisions.yml)		divisions.json ↔ 磁碟目錄 ↔ convert.sh / lint-agents.sh 的 AGENT_DIRS ↔ workflow path 過濾，全部要一致；每個 division 至少 1 個 agent 檔 ./scripts/check-divisions.sh
工具整合一致性scripts/check-tools.sh
(check-tools.yml)		新增工具整合時：tools.json ↔ convert.sh ↔ install.sh ↔ .gitignore ↔ integrations/<tool>/README.md 全部對齊 ./scripts/check-tools.sh
安裝器回歸測試scripts/test-install.sh
(test-install.yml)		在拋棄式沙箱（絕不用你真正的 $HOME）中釘住安裝器的可觀察契約：檔案落在哪裡、--path 優先於工具的環境變數、--division / --agent / --agents-file 篩選、--dry-run 不寫任何東西、含空格的路徑可用。CI 在 Linux 與 macOS 上執行 ./scripts/test-install.sh
轉換輸出評測scripts/test-convert-outputs.sh
(check-tools.yml)		把每個工具的輸出重新產生到暫存目錄，檢查產品本身：description 完整往返、產生檔可被真正的 YAML/TOML parser 解析、每個工具恰好為每個 agent 產生一份輸出、來源檔以桌面 App 讀取的方式解析。有意修改轉換器時會回報 manifest drift——檢視差異後用 --update 重跑並提交更新後的 scripts/convert-outputs.sha256，讓審核者一眼看出影響範圍。manifest 每個 agent 一行、每個工具一行，雜湊跨平台一致（正斜線路徑、LF 換行），Windows checkout 產生的檔案相同。新增／修改 agent 造成的 drift 在 PR 上僅為提示性，不會擋合併。CI 對每個 PR 執行 ./scripts/test-convert-outputs.sh
（更新 manifest 加 --update）
💡 環境需求：bash（Windows 用 Git Bash 即可）＋ python3（原創性檢查需要）。
✅ 為什麼有這些檢查？（官方原話大意）大家正在用這些 agent 打造出真正出色的東西，每天有數千人在十幾種工具上依賴它們。這很棒——但也代表某個轉換器的小疏失、或某個檔案裡多了一個引號，會悄悄地同時影響所有人。在本地跑這套測試，就是讓下游所有人都能順暢使用的方式。大約只要一分鐘，就能保證你的作品在每個工具、對每個人，都完全以你撰寫的原樣送達。謝謝你願意多走這一步——這是給素未謀面的人一份真正的善意。

9. 風格指南

寫作

  • 具體：「減少 60% 頁面載入時間」，不是「讓它更快」
  • 落地：「用 TypeScript 寫 React 元件」，不是「做 UI」
  • 令人印象深刻：給人格，不要公司官腔
  • 實用：真實可執行的程式碼，不是虛擬碼

格式

  • 章節標題帶 emoji（🎯🧠📋）方便掃讀
  • 程式碼一律用 code block 並標語言（語法高亮）
  • 比較選項或指標用表格；重點用 粗體、術語用 code
  • 程式碼範例四要素：語言標註、關鍵概念註解、可執行、現代最佳實踐

語氣

  • 專業但親切——不過度正式也不隨便
  • 自信不自大——「這是最佳做法」，不是「或許你可以試試…」
  • 有幫助但不包辦——假設使用者有能力，提供深度
  • 人格驅動——每個 agent 有獨特聲線

10. 常見地雷

地雷後果解法
CRLF 換行（Windows 常見）lint ERROR：frontmatter 解析失敗，錯誤訊息還很誤導存檔用 LF；已污染就 perl -i -pe "s/\r$//" 檔案；repo 的 .gitattributes 規定 LF
把 integrations/ 的轉換產出 commit 進去PR 被要求重做或直接關閉產出物永不提交；新工具整合要自己加 .gitignore 規則
換皮 agent（改個平台/國家名就當新的）原創性檢查 ≥40% 直接 FAIL做在地化就要讓平台、打法、範例真的不同
章節標題全改成中文/自創名稱convert.sh 無法拆分 Persona/Operations，lint 給 WARN章節標題保留英文關鍵字（Identity、Core Mission…）
一個 PR 改幾十個 agent官方明言必關閉一個 PR 一個檔；大改動先開 Discussion
照抄廠商文件當 agent 內容審核不過——「穿著 agent 外衣的快速入門」引用文件連結；保留人格、workflow、專業判斷

11. 番外：在本機 Kimi Code 測試新 Agent

寫好 agent 後、發 PR 前，可以直接在本機用 Kimi Code 實測（對應 CONTRIBUTING 的「Test Your Agent」要求）：

# 1. 重新產生 Kimi 整合檔（只轉 kimi 會快很多）
./scripts/convert.sh --tool kimi

# 2. 安裝到本機
./scripts/install.sh --tool kimi

# 3. 用你的新 agent 啟動實測
kimi --agent-file ~/.config/kimi/agents/your-agent-name/agent.yaml

如果只想快速試單一 agent 而不重裝全部，也可以直接把 agent 檔內容貼進某個測試專案的 AGENTS.md 來模擬人格。
