1. Overview: Project Structure & Contribution Types

The Agency is a pure-Markdown agent collection. Each agent is a single .md file under its division's top-level directory. Conversion and installation are handled by scripts — contributors only need to write one good .md file.

PathNatureDescription
engineering/, marketing/, … 18 directoriesDivision (agent source)Where agent .md files live; the authoritative list is divisions.json at the repo root
divisions.jsonSingle source of truth for divisionsDefines each division's label, icon, and color; CI verifies it against on-disk directories with check-divisions.sh
tools.jsonSingle source of truth for tool integrationsDefines conversion targets for 17 tools — Claude Code, Cursor, Kimi, Codex, and more
integrations/Output, not sourceOutput directory of convert.sh; only each tool's README.md is tracked by git, everything else is gitignored
strategy/, examples/Not divisionsPlaybooks and examples; no agent frontmatter
scripts/Infrastructureconvert.sh (conversion), install.sh (installation), lint-agents.sh (format checks), check-agent-originality.sh (originality), and more

Four ways to contribute

  • Add an agent — one new .md file (the most welcome contribution)
  • Improve an existing agent — add real examples, update code samples, refine workflows, add success metrics, fix typos
  • Share success stories — Discussions posts, README case studies, blog posts, video tutorials
  • Report issues — search existing issues first; include clear reproduction steps and your use case
💡 Officially stated: the fastest PRs to merge are "one markdown file" — adding or improving a single agent. Anything beyond that scope usually needs a Discussion first to align on direction.

2. Adding an Agent: The Complete 9-Step Process

1Fork & Clone the Repository
# Fork msitarzewski/agency-agents on GitHub, then:
git clone https://github.com/<your-account>/agency-agents
cd agency-agents
2Choose Its Division

Browse the division directories and find the closest fit (web frontend → engineering/, community building → marketing/, penetration testing → security/, literature & evidence synthesis → research/). The authoritative list of 18 divisions is divisions.json. Only consider proposing a new division (see §4) when nothing fits — specialized/ is the catch-all for agents that fit nowhere else.

3Create the File, Follow Naming Conventions

Filename format: <division>-<agent-name>.md, all lowercase, kebab-case. Examples:

engineering/engineering-frontend-developer.md
marketing/marketing-xiaohongshu-specialist.md
game-development/unity/unity-architect.md   ← game-development has engine subdirectories
4Write the YAML Frontmatter
---
name: Agent Name
description: One-line description of the agent's specialty and focus
color: colorname or "#hexcode"
emoji: 🎯
vibe: One-line personality hook — what makes this agent memorable
services:                              # optional — only if the agent depends on external services
  - name: Service Name
    url: https://service-url.com
    tier: free                         # free / freemium / paid
---

name, description, and color are required by CI (missing = hard ERROR); emoji, vibe, and services are optional.

5Write the Body from the Template (Persona + Operations)

Sections fall into two semantic groups. convert.sh splits agents into per-tool formats based on section headings, so keep the grouping and the English heading keywords (Identity / Core Mission / Critical Rules…):

GroupSectionContent
Persona
(who this agent is)		🧠 Your Identity & MemoryRole / Personality / Memory / Experience
💭 Your Communication StyleTone, signature phrasing, communication patterns
🚨 Critical Rules You Must FollowDomain-specific hard rules and boundaries
Operations
(what this agent does)		🎯 Your Core MissionPrimary responsibilities (each with a concrete deliverable) + default requirements
📋 Your Technical DeliverablesConcrete outputs: code examples, templates, frameworks, documents
🔄 Your Workflow ProcessPhased, step-by-step process
🎯 Your Success MetricsQuantifiable outcome metrics (with numbers)
🚀 Advanced CapabilitiesAdvanced techniques

See §5 for the full template skeleton.

6Local Validation: Lint + Originality + Convert-Output Checks
# Format check (required fields, line endings, sections)
./scripts/lint-agents.sh engineering/engineering-your-agent.md

# Originality check (compared against all 279 agents; defeats find-replace reskins)
./scripts/check-agent-originality.sh engineering/engineering-your-agent.md

# Convert-output check (confirms your agent survives every tool's converter intact)
./scripts/test-convert-outputs.sh

Originality thresholds: similarity ≥ 20% warns, ≥ 40% is flagged as a duplicate (CI failure). The highest similarity anywhere in the existing roster is only ~1.5%, so double digits are an anomaly. The check neutralizes country/platform proper nouns, so reskins like "swap TikTok for Douyin" can't escape it.

test-convert-outputs.sh regenerates every tool's output into a scratch directory and checks the product, not the syntax: every agent's description round-trips intact, every generated file parses with a real YAML/TOML parser, every tool emits exactly one output per agent, and every source file parses the way the desktop app reads it. Adding or editing an agent changes the generated product, so it will report manifest drift naming your agent — that's expected, and on pull requests it is advisory: CI prints it but does not fail. You don't need to touch scripts/convert-outputs.sha256; the maintainers regenerate it when your PR lands. (Running --update yourself is fine too — the manifest has one line per agent, so it won't conflict with anyone else's PR, and the hashes are identical on Windows, macOS, and Linux.)

7Test in Real Scenarios

The project asks for "battle-tested, not theoretical": actually use the agent (e.g. load it in Kimi Code on a real task — see §11), then iterate based on the results.

8Commit & Push to Your Fork
git checkout -b add-your-agent-name
git add engineering/engineering-your-agent.md
git commit -m "Add Your Agent Name specialist"
git push origin add-your-agent-name
9Open a Pull Request
  • Title format: Add [Agent Name] - [Category]
  • Body: what the agent does, why it's needed (what gap it fills), how you tested it
  • Complete the PR template checklist (see §8)

Then the review loop: community feedback → iterate → maintainer approval → merge.

3. Improving an Existing Agent

Improving existing agents is just as welcome as adding new ones, and follows the same "one-file PR" route. The officially listed improvement directions:

  • Add real-world examples and use cases
  • Update code examples with modern patterns (e.g. old syntax → current framework idioms)
  • Refresh workflows to current best practices
  • Add success metrics and benchmarks
  • Fix typos, improve clarity, complete documentation

Process

  1. Fork → branch (e.g. improve-frontend-developer-examples), same as adding
  2. Edit the target .md file; run ./scripts/lint-agents.sh <file> afterwards to confirm nothing broke
  3. Commit (e.g. Improve frontend-developer: add React 19 examples) → push → open PR
  4. In the PR body, explain "what changed and why it's better"
⚠️ Do not batch-edit large numbers of existing agents in one PR — even well-intentioned reformatting causes merge conflicts for other contributors, and the maintainers explicitly close such PRs. For broad restructuring, open a Discussion first.

4. Proposing a New Division

A new division is an "architectural change" — always open a Discussion first to reach consensus. Once approved, the technical steps:

  1. Create the new directory with at least 1 agent file with frontmatter inside
  2. Add an entry to divisions.json: label (display name), icon (Lucide icon name, PascalCase), color (hex)
  3. Add the directory name to the AGENT_DIRS array in both scripts: scripts/convert.sh and scripts/lint-agents.sh
  4. Update the CI path filters (paths in .github/workflows/lint-agents.yml)
  5. Run ./scripts/check-divisions.sh to verify — it checks that divisions.json ↔ on-disk directories ↔ script lists are all consistent, and fails if not
⚠️ strategy/ (playbooks) and integrations/ (convert output) are never divisions and must not be added to the division list.

- Primary responsibility 2 (with concrete deliverable)

## 📋 Your Technical Deliverables
Concrete outputs: code examples / templates / frameworks / documents

## 🔄 Your Workflow Process
1. Phase one: Discovery & research
2. Phase two: Planning & strategy
3. Phase three: Execution & implementation
4. Phase four: Review & optimization

## 💭 Your Communication Style
How it communicates, example phrasing, tone

## 🔄 Learning & Memory
Learning from successful patterns / failed approaches / user feedback / domain evolution

## 🎯 Your Success Metrics
Quantitative metrics (with numbers), qualitative metrics, performance benchmarks

## 🚀 Advanced Capabilities
Advanced techniques and methods
✅ Keep the English keywords in section headings (Identity, Core Mission, Critical Rules, Communication Style…), because lint-agents.sh and convert.sh rely on them to recognize sections and split Persona / Operations. Missing the three recommended sections (Identity / Core Mission / Critical Rules) triggers a lint WARN (doesn't block merge, but reviewers will see it).

Principles for External Services (services)

  • The agent must stand on its own — strip out the API calls and the persona, workflow, and expertise are still useful
  • Don't copy-paste vendor docs — reference them instead; the file should read like an agent, not a quickstart tutorial
  • Prefer services with a free tier, so contributors can test
  • Litmus test: "Does this agent serve the user, or the vendor?"

6. Design Principles: Dos & Don'ts

The Five Design Principles

  1. 🎭 Distinct persona — a unique voice and character, not "I'm a helpful assistant". Example: "By default I identify 3–5 issues and request visual evidence" (Evidence Collector)
  2. 📋 Concrete deliverables — real code examples, templates, frameworks; show actual output, not vague descriptions
  3. ✅ Success metrics — specific and quantifiable: "page loads under 3 seconds on 3G", "10,000+ combined karma across accounts"
  4. 🔄 Battle-tested workflow — step-by-step, tested in real scenarios, not theory
  5. 💡 Learning memory — which patterns to recognize, how to improve over time, what to remember across sessions

Side-by-Side

✅ Great agents have❌ Avoid
Narrow, deep specializationOver-broad scope (jack of all trades)
A unique persona and voiceGeneric "helpful assistant" persona
Concrete code / template examples (at least 2–3)No code examples, no deliverables
Quantifiable success metricsVague "I'll help you…" descriptions
Step-by-step workflowUntested theoretical approaches
Real-scenario testing and iterationFind-replace reskins of existing agents

The manifest holds one line per agent and one per tool, with platform-neutral hashes (forward-slash paths, LF endings), so a Windows checkout produces the same file. Drift caused by adding/editing an agent is advisory on PRs and does not block merge. CI runs it on every PR ./scripts/test-convert-outputs.sh
(add --update to refresh the manifest)
💡 Requirements: bash (Git Bash works on Windows) + python3 (needed by the originality check).
✅ Why these checks exist (in the maintainers' words): people are building genuinely remarkable things on top of these agents, and thousands rely on them every day across a dozen different tools. That's wonderful — and it means a small slip in one converter, or a stray quote in one file, quietly reaches all of them at once. Running the suite locally is how we keep that smooth for everyone downstream. It takes about a minute, and it means your work arrives exactly as you wrote it, in every tool, for everyone. Thank you for taking the extra step — it's a real kindness to people you'll never meet.

8. PR Conventions & Review Process

Three Fates for a PR

✅ Always welcome💬 Open a Discussion first❌ Always closed
Adding one agent (one .md)
Improving an existing agent's content/examples/persona
Fixing typos, clarifying docs		 New tools, build systems, CI workflows
Architectural changes (new directories, new scripts, site generators)
Changes spanning many files
New integration formats or platforms		 Committing build output (converted integrations/ files, _site/)
Batch-editing existing agents without discussion
Near-duplicate "reskin" agents

Branch / Commit / Title Formats

git checkout -b add-agent-name                    # branch
git commit -m "Add [Agent Name] specialist"       # commit
PR title: "Add [Agent Name] - [Category]"         # PR

PR Template (Official Checklist)

## Agent Information
**Agent Name**: [name]
**Category**: [engineering/design/marketing/etc.]
**Specialty**: [one-line description]

## Motivation
[Why is this agent needed? What gap does it fill?]

## Testing
[How did you test it? Real-world usage scenarios?]

## Checklist
- [ ] Original — not a near-duplicate (ran scripts/check-agent-originality.sh)
- [ ] Follows the agent template structure
- [ ] Includes a persona and voice
- [ ] Has concrete code/template examples (at least 2–3)
- [ ] Defines success metrics
- [ ] Includes a step-by-step workflow
- [ ] Proofread and properly formatted
- [ ] Tested in a real scenario

Review Process

Community review (feedback from other contributors) → iterate → maintainer approval → merge. Recognition: README acknowledgments, release-notes mentions, "Agent of the Week" features, and credit inside the agent file.

9. Style Guide

Writing

  • Be specific: "reduce page load time by 60%", not "make it faster"
  • Be concrete: "write React components in TypeScript", not "do UI"
  • Be memorable: give it personality, not corporate speak
  • Be practical: real, runnable code, not pseudocode

Formatting

  • Section headings carry emoji (🎯🧠📋) for scannability
  • All code in fenced code blocks with a language tag (syntax highlighting)
  • Use tables to compare options or metrics; bold for key points, code for terms
  • The four properties of a good code example: language tagged, key concepts annotated, runnable, modern best practices

Tone

  • Professional but approachable — neither stiff nor sloppy
  • Confident, not arrogant — "this is the best practice", not "maybe you could try…"
  • Helpful without doing everything — assume a capable user, provide depth
  • Personality-driven — every agent has a unique voice

10. Common Pitfalls

PitfallConsequenceFix
CRLF line endings (common on Windows)Lint ERROR: frontmatter parsing fails with a misleading error messageSave with LF; if already polluted, perl -i -pe "s/\r$//" file; the repo's .gitattributes mandates LF
Committing converted output from integrations/PR gets sent back or closed outrightGenerated output is never committed; new tool integrations must add their own .gitignore rule
Reskin agents (swap a platform/country name and call it new)Originality check ≥40% = hard FAILIf you're localizing, make the platforms, tactics, and examples genuinely different
Translating or renaming section headingsconvert.sh can't split Persona/Operations; lint WARNKeep the English keywords in headings (Identity, Core Mission…)
Editing dozens of agents in one PRExplicitly always closedOne PR, one file; open a Discussion for big changes
Copy-pasting vendor docs as agent contentRejected in review — "a quickstart wearing an agent costume"Link to the docs; keep the persona, workflow, and professional judgment

11. Extra: Testing a New Agent Locally with Kimi Code

After writing your agent and before opening the PR, you can battle-test it locally with Kimi Code (matching CONTRIBUTING's "Test Your Agent" requirement):

# 1. Regenerate the Kimi integration files (converting only kimi is much faster)
./scripts/convert.sh --tool kimi

# 2. Install locally
./scripts/install.sh --tool kimi

# 3. Launch a real test run with your new agent
kimi --agent-file ~/.config/kimi/agents/your-agent-name/agent.yaml

If you just want to try a single agent quickly without reinstalling everything, you can also paste the agent file's content into a test project's AGENTS.md to simulate the persona.
